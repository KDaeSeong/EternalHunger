2026-09-05. G1.3(무료 보정 없는 성장), G2.3(실제 전투 인과관계), G3(공유 자원)의 잔여 작업을 구체화한 문서다. **1차 감사는 소스 읽기만 했고 재현 시험·빌드·경기는 실행하지 않았다.** 발견한 분기를 기본 경기에서 관측된 현상으로 단정하지 않는다. 후속 턴에서 A4의 거래 처리, A1/A2의 레시피 없는 보정 제거, A3의 실제 T1 시작 지급, A5의 사냥 사망/정산 경계 소스와 검사 코드를 수정했다. 실행 검증은 하지 않았으며 아래에서 감사 당시와 후속 수정 상태를 구분한다.

## 확인된 예외와 재현해야 할 조건

### A1. 레시피 부재 시 루트 완료를 장비 생성으로 대신함

**1차 감사 당시:** `gearDirectorRuntime.js:49`의 `day1HeroGearDirector`는 카탈로그에 레시피가 하나라도 있으면 반환했다. **레시피가 전혀 없는 경우에는** `forceRouteCompletion`이 일반 추상 보정 허용 여부를 우회할 수 있었다. 이 분기는 재료를 소비하지 않고 부족한 장비 부위에 카탈로그 장비를 추가했다(당시 `:72` 이후). 일반 보정 분기는 특정 레시피가 아닌 임의 하급 재료를 소비해 장비를 올렸다. 후반 `lateGameGearDirector`도 같은 레시피 부재 조건에서 하급 1개+특수 1개를 임의 장비로 바꿨다.

호환 호출은 남아 있다: `phaseActorQueuedActionStepRuntime.js`, `phaseActorActionStepRuntime.js`, `phaseActorPostActionRuntime.js`, `phaseCraftActionRuntime.js`, `phaseRouteProgressRuntime.js`. 후속 수정에서 호출 대상의 지급/소비/완성 처리 본문은 제거했다. 정상 제작은 기존 실제 레시피 제작 행동이 담당하며, 호환 함수는 레시피가 없을 때 원인만 반환한다.

기본 실제 레시피 카탈로그에서는 앞의 차단 조건이 있으므로 이 결과를 기본 경기의 무상 장비 발생 증거로 쓰지 않는다. 재개 후에는 레시피 없는/일부 빠진 카탈로그와 모든 강제 완료 옵션을 넣어도 재료 없는 장비 증가가 없어야 한다. 데이터 누락은 제작 불가 사유로 드러나야 하며, 장비 생성으로 숨겨서는 안 된다.

### A2. 특수 재료 하나로 레시피 없는 임의 장비 제작

**1차 감사 당시:** `gearImmediateSpecialCraftRuntime.js:93` 이후 실제 레시피 분기는 전체 재료를 소비했다. 그러나 그 조건을 통과하지 않으면 당시 `:137`에서 특수 재료 1개만 소비하고 고른 장비를 추가하며, `:160`에서 `pvpBonus` 0.35 또는 0.55를 반환했다. 이 값을 공격력 증가로 단정하지 않는다. 호출자는 별도의 PvP/위험 상태에 전달했다. 후속 수정에서 해당 임의 지급과 보정 반환을 제거했다.

재개 후 완료 기준: 전체 레시피가 없는 경우 아이템/관련 보정 값 증가 없음, 부족한 다른 재료를 특수 재료 하나가 대체하지 않음, 실제 레시피 성공 시에만 정확한 수량 소비. 이미 작성된 기본 레시피 검사를 삭제하거나 완화하지 않는다.

### A3. 시작 카탈로그의 누락이 생성 무기·상위 장비로 바뀔 수 있음

**1차 감사 당시:** `gearCatalogRuntime.js:82`는 무기 종류에 맞는 카탈로그가 없을 때 생성 무기를 만들었다. 근접 티어 선택은 하위가 없으면 상위 티어를 선택했다. 시작 장비 호출 `phaseSpawnRuntime.js:117`은 목표 T1이지만 `allowNearestTier: true`였다. 후속 수정에서 생성 무기와 상위 대체를 제거하고 시작 지급은 정확한 T1로 제한했다.

재개 후 완료 기준: 지원 무기별 실제 T1과 신발 T1, 필수 항목 누락/삭제/상위 티어만 존재하는 카탈로그에서 시작 지급과 경고 확인. 정상 시작 지급은 보존하되 데이터 누락을 숨긴 상위 성장 보정과 구분해야 한다. 현재 기본 24인에서 이 문제가 실제 발생했는지는 확인하지 않았다.

#### A1/A2/A3 후속 소스 수정 — 실행 검증 대기

2026-09-05. 검증 중단을 유지하며 다음 소스 변경과 검사 작성만 했다.

- A1: 조기 루트/후반 보정의 임의 재료 소비, 장비 지급, 강제 완성 처리를 제거했다. 호출 이름/공개 내보내기는 보존한다. 레시피가 있는 정상 경기는 기존 제작 행동에 맡기며 추가 제작 기회를 주지 않는다. 유효한 제작법이 전혀 없으면 시스템 로그로 알리고, 같은 연속 알림은 저장되는 키로 중복 억제한다.
- A2: 특수 재료의 실제 T5/T6 레시피를 선택해 기존 인벤 제작기를 호출한다. 부족한 다른 재료를 특수 1개가 대체하지 않으며, `pvpBonus`는 0이다. 실제 제작이 성공할 때만 일/페이즈 횟수를 반영한다. 해금 시점·초기 성장 우선·횟수 제한을 보존하고 사망한 실험체의 이 즉시 제작 경로를 차단했다. 구형 `ensureRoomForEquipment`는 내보내기 호환용으로만 남으며 현재 소스 호출은 없다.

- A3: 카탈로그 출처 선호보다 요청 부위·무기 종류·티어를 먼저 맞춘다. 정확한 T1이 다른 출처에 있어도 놓치지 않으며, 없으면 생성 무기/상위 티어로 대신하지 않는다. 시작 지급은 실제 받은 장비만 장착하고 무기·신발 수령 인원을 집계한다. 누락과 가방 수령 실패는 로그와 `_starterLoadoutIssues`로 구분한다. 1회 지급과 기존 시작 식량은 유지한다.

### A4. 키오스크 선택과 실제 지급 사이의 자원 조건이 보장되지 않음

**1차 감사 당시 소스:** `phaseProcurementActionRuntime.js:84` 구매는 아이템을 먼저 추가한 뒤 잔액을 `max(0, 잔액-가격)`으로 만들었다. 해당 실행 분기에 현재 잔액 충족 검사가 없었다. 당시 `:113` 교환과 `:143` 판매도 현재 보유 수량을 확인하지 않았다. `inventoryRules.js`의 소비 함수는 부족한 수량을 오류로 반환하지 않고 있는 만큼만 차감한다. 후속 수정에서는 이 범용 소비 함수를 바꾸지 않고 거래 확정 전에 전체 필요 수량을 확인한다.

따라서 다음은 **소스에서 도출한 미실행 재현 조건**이다: 잔액 0인 유효 구매 요청, 재료가 사라진 교환 요청, 이미 판매한 물건의 요청 재사용. 아이템/크레딧이 늘지 않아야 한다. 계획 단계가 처음에 조건을 검사하더라도 실제 반영 경계의 보장이 필요하다. 현재 정상 행동 계획에서 이런 상태가 얼마나 발생하는지는 측정하지 않았다.

완료 기준은 현재 잔액·재료·가방·생존 상태를 반영 직전에 확인하고, 성공 시 소비/지급을 함께 반영하는 것이다. 부분 수령 가격·판매 실패·중복 실행의 기준도 명시해야 한다.
