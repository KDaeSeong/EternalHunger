# 관전 시작의 결합 지연 분리

2026-09-24. 앞선 `e4347eb3…` 동일 입력 x8 세 경기에서 개별 Long Task는 189/196/175ms였지만, 시작 작업이 같은 긴 프레임에 합쳐져 LoAF 256.1/199.5/270ms를 기록했다. 원자료는 `artifacts/observer-sequential-x8-browser-20260924.json`이다. 평균 RAF 빈도나 개별 작업 합격으로 이 지연을 지우지 않는다.

## 변경 계약

- 기존 `scheduler.yield()` 경로는 작업을 나누지만 계속 실행할 작업을 우선 예약한다([Chrome 공식 설명](https://developer.chrome.com/blog/use-scheduler-yield)). 이번 관측은 준비 작업과 첫 성장 작업이 별도 task여도 같은 LoAF에 귀속되는 경우다.
- 페이즈 준비 직후에만 `requestSimulationFrameYield`를 사용한다. 보이는 문서는 RAF 콜백을 거친 뒤 별도 timer task에서 이어 간다. RAF 자체는 다음 repaint 전에 호출되므로 그 콜백에서 Promise를 바로 완료하지 않는다([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)). 이는 화면 갱신 기회이며 실제 presentation 완료 보장은 아니다.
- 숨김/RAF 미지원 환경은 기존 scheduler 또는 0ms timer 경로를 유지한다. 대기 중 숨김 전환, RAF 요청 실패, 콜백 미도착에 대한 100ms fallback timer를 두고, 완료 시 RAF·두 timer·visibility listener를 정리한다. 실제 타이머 실행은 브라우저 스케줄링/백그라운드 제한을 받으므로 100ms 이내 완료를 보장한다는 뜻이 아니다.
- 잦은 행동 프레임과 페이즈 마무리는 기존 yield를 유지한다. 원자적 상태 게시 위치, 난수, 게임 내 시간, 처리 순서, 전투/파밍 수치와 궁극기 사냥 금지는 변경하지 않는다. 저장 기록의 엔진 버전 검사는 그대로다.
