# 초기 장비 목표의 별칭 일치

기기 아이템 저장은 기존 카탈로그의 `itemKey`를 유지하면서 `externalId` 별칭을 수정할 수 있다. 성장 진행도는 `itemKey`·`externalId`·실제 ID를 원래 카탈로그 순서로 검색하지만, 초기 경로 색인은 선호 키 하나와 ID만 저장했다. 그 결과 별칭으로 지정한 투구가 성장 목표에는 남아도 초기 경로에서는 일반 후보로 밀려 다른 재료를 향할 수 있었다.

`buildItemIndexes`가 세 식별자를 모두 정규화해 같은 순서의 첫 항목에 연결하도록 수정했다. `byId`의 실제 ID 조회, 다른 곳의 선호 키 표시/가중치, 레시피·제작 비용·수량·슬롯·지도·능력치·시작 예산은 유지한다. 새 전역 캐시는 추가하지 않았다. 뒤의 실제 성장 계획은 이미 선호 키로 정규화한 뒤 제작하므로 제작 로직을 고칠 필요는 없었다.

## 현재 확인

- 수정 전 실제 소스에서 신규 회귀 11그룹 중 3개 통과·8개 실패, 종료 1을 기록했다. 원본 세 파일과 로그/지문을 보존했다.
- 수정 후 현재 코드만 읽는 11그룹은 모두 통과했고, 비공개 자료 읽기 차단 실행의 접근 시도는 0이었다. 실제 기기 프로필 저장/재읽기, 5부위 경로, 모든 별칭, 먼저 등록된 별칭 충돌, 공백·임의 문자열, 알 수 없는 목표, 입력/난수 보존과 실제 같은 등급 목표 제작을 다룬다. 이 제작 경계의 미리 준비된 재고는 자연 경기 결과와 구분한다.
- 고정 확장 커스텀 2조건은 각각 원래 24명·지도·능력치·빈 가방·예산·팀·지역을 유지하고 두 팀의 네 대원에게 직접 목표를 지정했다. 새 엔진 `a1bebd54…`에서 8/8 지정 대원이 첫밤 전 실제 제작·장착을 완료하고 각 조건의 전체 동일 입력 재경기가 프레임·사건·로그·최종 상태/난수와 일치했다. 이는 새 별칭만의 경기 인과 실험이나 전체 48명 완성률·생존율·모든 조합의 성공률이 아니다. 이 두 조건은 예전에 선언된 HF4 A/C 편성의 커스텀 입력이며, 미달 상태인 G5.2 고정 편성 8회 비교를 재시도한 것이 아니다.
- 공개 확인용 구조 검사 15건은 실제 원본의 선호 키 전용 색인을 음성 대조로 유지하고, 새 Map/행/ID 연결과 Worker 요청·의존성 추출을 검사했다. 문자열 표식만으로 새 기능 전달을 판정하지 않는다.

## 감사 판정 교정

`audit-custom-item-support.mjs`가 현재 지원하는 회복약을 여전히 미지원으로 가정해 `HF6-USE`를 실패 처리했다. 정상 회복의 실제 HP·수량 소비를 양성으로 확인하고, 별도 `HF6-UNSUPPORTED`에서 알 수 없는 필드·지원 효과와 알 수 없는 필드의 혼합·음수 회복을 스키마와 수동/자동 사용에서 거부하며 인물 전체가 보존되는지 확인한다. 실제 6항목이 통과했지만 이 진단의 `implementationComplete:false`와 계정/실제 UI/원래 평가 자료 부재 한계는 유지한다. 기기 편집기가 없다는 오래된 문구도 실제 화면 미검증이라는 정확한 한계로 바꿨다.

## 인수 경계

성장·제작·소모품·장비·고정 확장 경기/재경기·재현/Worker·지원 감사·공통 화면·린트의 10명령과 생산 빌드 `upCvVJAI6AynVa0aVBThQ`가 실제 종료 0이며 선언 입력 1,310개는 같다. 공개 검사 도구의 최초 컴파일러 표현식 인식 실패는 별도 보존하고, 동일한 ID Map 기록과 별칭 배열에 한정해 보강했다. 커밋/공개 전달은 별도의 불변 소스·전체 파일·실제 Worker 주소/의존성 증거로 판정한다. Node VM Worker 검사를 전경 브라우저·UI 속도 증거로 삼지 않는다. 이전 `3102c32c…`와 `90deb53d…`의 비교·사람·전경 관측은 역사 자료이며 새 엔진의 합격으로 승계하지 않는다. 화면 조작은 물리적 Esc 중단 상태다. 원래 G1~G5 → 문명 → 스무고개 → 스타리그 → 회사 전체 목표와 넓은 커스텀/전략, 실제 계정·사람·자연 로그인 만료 관문은 활성·미완료다.
