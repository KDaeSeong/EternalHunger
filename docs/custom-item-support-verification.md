## 2026-10-03 계정 쿠키 조회·효과·실제 DB 왕복

클라이언트 엔진은 변경하지 않았다. 새 일회용 계정과 별도 MongoDB에서 실제 인증·아이템 편집·카탈로그·저장 슬롯 HTTP 경로를 연결하여 다음 결함을 순서대로 재현했다.

- `Item`의 식별자 인덱스가 `partialFilterExpression`과 `sparse`를 함께 선언하고 지원하지 않는 `$ne` 조건을 사용하여 새 DB 초기화가 `CannotCreateIndex (67)`로 실패했다. 중복되는 `sparse`를 제거하고 문자열/비어 있지 않은 값 조건을 `$type`·`$gt`로 표현했다. 동일 소유자의 중복 식별자는 거부하고 다른 소유자의 동일 식별자와 빈/누락된 옛 식별자는 허용하는 실제 고유성 검사를 통과했다. 기존 사용자/운영 DB의 인덱스 삭제·동기화·마이그레이션은 실행하지 않았다. 제약의 공식 근거는 [MongoDB 부분 인덱스 문서](https://www.mongodb.com/docs/manual/core/index-partial/)를 따른다.
- 브라우저 인증은 HttpOnly `token` 쿠키를 사용하는데 선택적 사용자 조회는 Authorization만 읽어, 실제 로그인·아이템 생성 뒤에도 `/api/public/items`가 공유 아이템만 반환했다. 서명/만료 검증을 유지하면서 쿠키도 읽고, 이미 검증된 사용자와 명시한 기존 헤더의 우선순위는 보존했다. 익명·위조/만료 쿠키 및 다른 계정에는 해당 소유자의 아이템이 노출되지 않는다.
- 소유자 구분을 수정한 뒤에도 공개 카탈로그의 필드 선택에서 `consumeEffect`·`equipmentEffects`가 빠져 회복량과 파열 효과가 유실됐다. 저장된 두 필드를 시뮬레이션 카탈로그에 포함했다. 실제 조합식 재료/수량·비용·결과 수량·능력치와 두 효과의 저장→조회→DB 재연결 후 복원을 확인했다.
