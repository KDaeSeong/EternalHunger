# 구형 MyAnimecraft 경기 시뮬레이션 정적 분석

> 쉬운 설명이 필요하면 [`original-match-simulation-easy.md`](./original-match-simulation-easy.md)를 먼저 읽는다.

분석일: 2026-09-03

## 범위와 증거 수준

이 문서는 기존 Ghidra 프로젝트의 32비트 x86 프로그램 `MyAnimecraft.exe`를
헤드리스 모드로만 디컴파일해 작성했다. 게임 창과 EXE는 실행하지 않았다.

- **확인**: 명령어 또는 디컴파일 결과로 데이터 흐름과 상수를 직접 확인했다.
- **강한 추론**: 코드 흐름은 확인했으나 심볼이 없어 게임 용어의 정확한 이름을
  추정했다.
- **미확인**: 런타임 관찰 또는 추가 함수의 완전한 의미 복원이 필요하다.

## 한 줄 결론

원본은 선수 총점을 비교해 한 번 주사위를 던지는 방식이 아니다. 선수 8능력치,
컨디션, 레벨, 사용 후 소거되는 능력별 보너스, 맵 6수치와 고정 LCG 난수를 매 논리 tick에 섞어
두 진영의 파생 능력을 다시 만들고, 종족 조합별 AI가 5개 action 슬롯과 두 종류의
전력/자원 지표를 계속 갱신한다. 승패는 그 지표의 비율이 임계값을 넘거나
4001번째 tick의 시간 제한 판정에 들어갔을 때 결정된다.

## 전체 흐름

```text
선수 원본 2명 + 현재 맵
        |
        v
작업 버퍼로 전체 레코드 복사
        |
        v
tick 증가 -> 8능력치 파생 roll -> 종족 조합별 AI/action 진행
        |                                  |
        +---------- 전력/자원 갱신 <-------+
        |
        v
200 tick 이후 조기종료 비율 검사
        |
        +-- 종료 안 됨 --> 다음 tick
        |
        +-- 4001 tick --> 전력 우세 측 승리
```

### 경기 입력 복사 — 확인

`FUN_0040F570`과 다음 경기 준비부인 `FUN_004460E0`은 다음 데이터를 통째로
작업 버퍼에 복사한다.

| 데이터 | 원본 | 작업 버퍼 | 크기/stride |
|---|---:|---:|---:|
| 선수 0 | `0x00542288 + id * 0xB38` | `0x0053B370` | `0xB38` |
| 선수 1 | `0x00542288 + id * 0xB38` | `0x0053BEA8` | `0xB38` |
| 맵 | `0x00614EF8 + id * 0x2C` | `0x0053CB08` | `0x2C` |

선수 레코드 앞부분은 `race(+0x00)`, `team(+0x04)`, 8개 float 능력치
`(+0x08..+0x24)`, 컨디션 관련 값 `(+0x28..+0x30)`, 레벨 `(+0x38)`을
담는다. 에디터의 필드 순서와 getter 주소를 함께 대조하면 8능력치는
컨트롤, 공격, 견제, 전략, 물량, 방어, 정찰, 센스 순서다.

## 난수 — 확인

### LCG 본체

- 전역 seed: `0x00539E7C` (초기 데이터값 `1`)
- seed 설정: `FUN_004ADD40`
- 다음 난수: `FUN_004ADD50`

```c
seed = seed * 0x343FDu + 0x269EC3u; // uint32 overflow 포함
result = (seed >> 16) & 0x7FFF;      // 0..32767
```

이는 고전 MSVC `rand()` 계열과 같은 LCG다. 같은 seed와 같은 호출 순서를
주면 경기 결과가 결정적으로 재현된다.

범위 래퍼도 확인됐다.

```c
// FUN_00401F60
boundedInt(n) = n >= 1  ?  rand() % n
              : n <= -1 ? -(rand() % -n)
              : 0;

// FUN_00401FD0: float로 반환
boundedFloat(n) = n >= 1.0f  ?  float(rand() % int(n))
                : n <= -1.0f ? -float(rand() % int(-n))
                : 1.0f;
```

`FUN_00409EA0`은 `rand() % 58`로 중복 없는 맵 번호를 만들고,
`FUN_00447390`은 일부 경기 상태에서 `rand() % 3`을 사용한다. 실제 경기의
능력치 roll은 `FUN_00443440 -> FUN_00401FD0 -> FUN_004ADD50` 경로로 seed를
소비한다.

## 선수 능력치가 경기 안으로 들어가는 방식 — 확인

### 1. 기본 능력 범위

각 능력 getter `FUN_00408200..FUN_004083C0`은 저장된 능력치에서
`816.0f`를 뺀 값을 반환한다. `FUN_00408A40..FUN_00408F80`은 여기에
컨디션과 해당 능력의 보너스를 적용한다.

```text
normalizedStat = storedStat - 816

normalCondition = clamp((storedCondition - 149) + conditionBonus, 80, 100)
effectiveRange  = min(1000, normalizedStat * normalCondition / 100)
                  + perStatBonus

rolledStat = boundedFloat(effectiveRange)
```

임시 컨디션 값 `player+0x2C`이 0이 아니면 80~100 clamp를 우회하고 그 값도
합산한다. 능력별 보너스는 `player+0x48..+0x64`에서 읽으며 파생값을 기록한
뒤 0으로 지운다. 보너스가 장비/일회성 효과라는 명칭은 **강한 추론**이지만,
그 값이 계산에 들어가고 소모되는 데이터 흐름 자체는 확인했다.

`FUN_00443440`은 최종 파생값을 1~1000으로 제한한 뒤 다시 `+816`하여
작업 선수 버퍼에 기록한다. 종족 조합별 tick 드라이버 여섯 곳은 이 함수를
호출한 뒤 race별 AI를 진행한다.

### 2. 레벨, 센스, 경기 시간

- 레벨 우위 보너스는 `(자기 레벨 - 상대 레벨) * 5`, 범위 `0..25`다.
- 동족전이면 센스 차이의 `1/6`이 주요 파생 능력에 추가된다.
- 공격·견제·물량·방어·정찰 쪽에는
  `(자기 센스 - 상대 센스) * tick / 8000`도 더해져 시간이 지날수록
  센스 차이가 누적된다.

### 3. 맵의 세 종족전 수치

현재 맵의 `T/Z(+0x20)`, `Z/P(+0x24)`, `P/T(+0x28)`는 단순 승률 보너스가
아니라 능력별 난수 폭을 바꾼다.

| 능력 roll | 맵 계수 |
|---|---|
| 전략, 센스 | `P/T / 100` |
| 공격 | `(200 - T/Z) / 100` |
| 물량 | `Z/P / 100` |
| 방어 | `T/Z / 100` |
| 컨트롤, 견제, 정찰 | 직접 계수 없음 |

또한 `T/Z`는 `FUN_00447C10`에서 action 완료 진행도의 공통 임계값으로도
사용된다. 이름과 사용처가 직관적으로 일치하지 않는 구형 구현의 특징이다.

### 4. 거리·자원·복잡도의 종족 상성

`FUN_00442EF0(side)`은 맵의 `rushDistance(+0x14)`, `resources(+0x18)`,
`complexity(+0x1C)`를 실제 종족 조합에 따라 다음처럼 바꾼다. 아래 race는
원본 코드 `2=T, 3=Z, 4=P`를 `1=T, 2=Z, 3=P`로 정규화한 값이다.

| 자기 vs 상대 | 기본 delta |
|---|---:|
| T vs Z | `(rushDistance - 50) * 4` |
| Z vs T | `(50 - rushDistance) * 4` |
| Z vs P | `(resources - 50) * 4` |
| P vs Z | `(50 - resources) * 4` |
| P vs T | `(complexity - 50) * 4` |
| T vs P | `(50 - complexity) * 4` |
| 동족전 | `0` |

그 tick에 계산된 전략값으로 이 delta를 보정한다.

```text
strategyFactor = ((strategy - 816) + 1000) / 1000

delta > 0 : delta *= strategyFactor
delta < 0 : delta /= strategyFactor
```

즉 전략이 높으면 맵의 유리함은 키우고 불리함은 줄인다. 이 결과는
공격·견제·물량·방어·정찰 파생값에 더해진다.

`FUN_00443200`은 같은 종족쌍/맵 수치에서 `* 60`인 별도 정수 보정을 만들며,
`FUN_0043F1F0`의 경기 후 8능력치 증감 폭에 들어간다. 이는 승패 시간 제한을
바꾸는 값이 아니다.

## tick 전투와 action 큐 — 확인 + 용어는 강한 추론

`FUN_0040F570`은 `tick(0x00615AC4)=0`으로 둔 뒤 종료 플래그가 설 때까지
다음을 반복한다.

```c
while (!finished) {
    ++tick;
    FUN_00447390();
}
```

GUI 경로는 선택된 속도만큼 이 논리 tick을 한 화면 갱신에서 여러 번 처리한다.
따라서 아래의 200/4000은 초가 아니라 **논리 스텝 수**다.

각 진영 전투 상태 stride는 `0xA0`이며, 적어도 다음 float 지표가 있다.

| 주소(진영 0 기준) | 초기값 | 확인된 역할 |
|---:|---:|---|
| `0x0053B224` | `1.0` | 최대/누적 계열 전력 지표 |
| `0x0053B228` | `0.0` | action 비용을 차감·환급하는 현재 자원 지표 |
| `0x0053B22C` | `100.0` | 승패 합산에 들어가는 두 번째 전력 지표 |

`FUN_0049A3E0`은 두 진영과 진영별 5개 action 슬롯을 초기화한다.
`FUN_00474070`은 action id/state/cost/progress를 기록하고 비용을
`0x0053B228 + side*0xA0`에서 뺀다. `FUN_00447C10`은 매 tick 진행도를
누적하고 임계값을 넘으면 거대한 race AI/state 함수 `FUN_00447DE0`로
action을 해결한다. `FUN_00447CE0`은 비용을 되돌리고 슬롯을 비운 뒤 현재
자원이 최대 지표를 넘지 않도록 clamp한다.

종족 조합별 드라이버는 동족 3개와 이종족 3개로 나뉘며 파생 능력,
현재/최대 전력, action 상태를 보고 서로 다른 선택 함수를 호출한다. 따라서
겉보기에는 자동 경기지만 내부적으로는 생산/공격/방어에 가까운 작은 RTS 상태
기계를 계속 돌리는 구조라는 해석이 가장 타당하다.

## 승패 판정 — 확인

`FUN_004460E0`이 진영 `localSide=0,1`을 순서대로 훑는다. 아래에서

```text
localPower = powerA[localSide] + powerB[localSide]
oppPower   = powerA[opponent]  + powerB[opponent]
```

이며 `opponent(0)=1`, `opponent(1)=0`이다. 경기 상태가 허용되고
`tick > 200`일 때 다음 순서로 종료를 검사한다.

1. `tick < 4001`이고 `oppPower / (localPower + 1000) > 2.0`이면 종료
2. 같은 구간에서 `oppPower / localPower > 10.0`이면 종료
3. `tick > 4000`이고 `oppPower / localPower >= 1.0`이면 종료

종료 분기에서는 `opponent(localSide)`를 결과 배열 `0x00615AE8[...]`에
기록한다. 따라서 검사 중인 `localSide`가 패자이고 그 상대가 승자라는 해석이
코드 흐름으로 확인된다.

4001번째 tick의 동률(`ratio == 1.0`)은 `localSide=0` 검사에서 조건을
만족하므로 코드상 side 1 승리로 기울어진다. 이는 정적 코드의 직접적인 결과지만
실제 정상 데이터에서 완전 동률이 발생하는지는 **미확인**이다.

`800`, `1600`, `2400` 분기는 승패 임계값이 아니다. 이미 종료가 결정된 뒤
경기 길이에 맞는 결과 메시지/연출 묶음을 고르는 분기다.

## 아직 확정하지 못한 부분

- `FUN_00447DE0` 및 수십 개 race별 선택 함수의 각 action id가 화면상
  어떤 빌드/유닛/전술 이름과 대응하는지는 아직 이름을 복원하지 않았다.
- `0x0053B224`, `0x0053B228`, `0x0053B22C`의 원 제작자 변수명은 없다.
  이 문서의 전력/자원 명칭은 읽기 쉬운 설명용이다.
- 아이템별 특수효과가 어느 파생치 또는 결과 처리 분기를 직접 바꾸는지는
  별도의 아이템 경로 분석이 필요하다.
- 창을 띄우는 런타임 검증은 사용자의 지시에 따라 하지 않았다. 이 문서는
  정적 분석으로 확정 가능한 동작과 코드상 결과만 기록한다.
