# Eternal Hunger 관전자 성능 검증

G4의 화면 부하와 동기화 범위를 다룬다. 자동 방어선은 실제 브라우저 FPS·메모리·반응성 증거를 대신하지 않는다.

## 2026년 10월 16일 로그와 사건 표시의 공동 갱신

서로 다른 Worker 메시지는 각각 microtask checkpoint를 거치므로 기존 microtask 묶음은 메시지 사이의 화면 갱신을 합치지 못했다. 화면용 로그와 사건은 이제 한 RAF에서 함께 공개하며, RAF가 지연되면 100ms 타이머를 사용한다. 전체 텍스트·사건 기록은 즉시 FIFO로 보존한다. 재경기 입력 교체는 옛 대기 사건을 버리고, 페이즈 초기화는 화면용 로그만 비우며, unmount는 예약과 대기열을 취소한다. 경기 종료 상태에서는 마지막 대기 기록도 공개한다.

실제 훅과 수명 모델에서 메시지 사이 microtask를 둔 새 검사는 수정 전에 실패하고 수정 뒤 통과했다. 공동 RAF 공개·100ms 대체·5,000사건 표시 한도·교체·초기화·늦은 취소 콜백·종료 공개를 포함해 13개가 통과했다. 내보내기 8개와 관련 관전·실시간 프레임 19개·표시 시계 15개 및 런타임 정적 검사도 종료 0이다. 엔진 `49abcafe…`, 빌드 `FrOf4CtTmvFaLnNk1BEaF`의 62페이지와 생성 Worker READY·140초·701프레임도 통과했다. 생성 파일 검사의 호스트는 고립 Node VM이다.

Windows Chromium 155, 1,280×720, 시드 `1789192220412`, 24명·8팀의 실제 원 경기와 같은 문서의 재경기 세 번을 x32로 마쳤다. 원 경기는 브라우저를 표시하지 않은 기능 표본이며, 종료 후 수동 측정 마감과 표시 상태 변경이 있어 전체 probe의 RAF 중앙값을 활성 관전 성능으로 쓰지 않는다. 아래 세 재경기는 브라우저 표시를 켠 상태에서 각각 원본의 사건 13,237개·최종 상태·종료 판정과 일치했고, 20:33.5에 4팀 3명이 생존했다. 정지·배속·입력 식별 변경은 0이며 비교 후 자동 중지 경계는 모두 `settled`다.

## 2026년 10월 15일 경기 실행기의 대기 방식

별도 Worker의 기본 task yield만 `scheduler.yield()` 지원 시 해당 기능을 사용하도록 변경했다. 미지원 환경은 기존 0ms 타이머로 대체하고, 함수의 receiver·Promise·오류 전파를 보존한다. Main의 렌더링 기회, 표시 시계의 양수 대기, 경기 시계·난수·사건 순서는 바꾸지 않았다. [WICG 스케줄링 명세 초안](https://wicg.github.io/scheduling-apis/#the-scheduler-interface)은 Worker 노출과 task continuation을 정의하며, [Chrome 설명](https://developer.chrome.com/blog/use-scheduler-yield?hl=en)은 중첩 타이머와 다른 양보 방식을 설명한다. 이 API 근거 자체는 실제 속도나 task-source 공정성의 증명이 아니다.

새 엔진 `2d554a8e…`의 양보·난수 경계 14개, Worker client 9개, 결과 준비 4개와 피해 26개·상태 23개·시전 28개·팀 전투 12개가 통과했다. 엔진·검사 소스 지문이 같은 빌드는 62페이지와 `FSvh_pygJhyAZSi3Vwmdw`를 생성했다. 실제 생성 Worker와 공유 청크의 고립 VM도 READY 및 첫 페이즈 140초·701프레임을 통과했다. 이 VM은 브라우저 Scheduler가 없는 타이머 대체 환경이다.

같은 PC의 로컬 완성 빌드, 1,280×720, 시드 `1789192220412`, 24명·8팀에서 원본과 같은 문서의 연속 재경기 세 번을 x32로 관전했다. 모두 20:33.5에 4팀 전원 생존으로 끝났고, 세 재경기는 각각 원본의 13,237사건·최종 상태·종료 판정과 일치했다. 정지·배속·입력 식별 변경은 0회이고 비교 후 자동 중지의 경계도 모두 `settled`였다.

**32배속 처리량과 연속 지연 기준은 실패다.** 재경기 간격은 28,990ms·43,144.9ms이고 외부 프로그램은 사용자 요청대로 유지했다. 직접 실행한 무거운 빌드·검사는 측정 뒤 시작했다. 모든 문서는 visible이었지만 마지막 표본의 RAF는 약 1Hz였다. 해당 p95는 히스토그램 상한 밖인 1,000.1~1,010ms 범위이며, visible이라는 이유로 실제 전경 표시·부드러운 관전으로 판정하지 않는다. 재경기 2의 2,042ms 작업은 probe 시작 후 25,047.5ms에 있었고, 재경기 3의 992.6ms LoAF는 시작 경계에 걸친 항목이다. 준비·비교·정지까지 포함한 probe 통계를 활성 경기만의 CPU 또는 paint 지연으로 바꾸지 않는다.

시작 heap은 첫 표본 뒤 낮아졌고 닫힌 세션 세 개의 journal·텍스트 로그·화면 사건·생존자·사망자 회수를 관측했다. 닫힌 재경기 기록 하나는 회수됐으며 두 개는 공유 도달 가능성이 있거나 회수 전이었다. 추적 대상 퇴출은 0이다. 이 표본의 비단조 추세를 전체 heap 안정성이나 누수 없음으로 일반화하지 않는다. 재경기 2의 실제 측정 라벨 앞뒤에 예상 밖 문자가 남은 값은 출력 근거에 그대로 보존했고 원인은 미확인이다.

새 버전의 세 재경기는 기능 정합성 표본이며, 이전 공개판과 외부 부하·전경 상태를 통제한 인과 비교가 아니다. 브라우저 Worker에서 스케줄러와 타이머 중 실제 선택한 분기는 계측하지 않았으므로 버전·지원 자료만으로 새 API 경로 실행을 확정하지 않는다. 최신 x1/x8, 성능 합격을 충족하는 전체 반복, 실제 브라우저 프로세스 재시작과 사람의 후속 이해도·재미 평가는 남는다. 출력 전용 근거는 기존 `artifacts/phase-worker-followup-20261015.json`의 `workerTaskSchedulingFollowup`이다.

같은 소스의 최종 release 검증은 종료 0이며 새 저장 입력 재경기의 14,133사건·6,488프레임과 실제 Node Worker/기준 실행의 11,648사건·5,840프레임·7,107로그·최종 상태·난수·종료가 일치했다. ## 2026년 10월 15일 생성 실행 파일의 시작 오류

공개 엔진 `01fcdc20…`의 가시 상태 평가 표본은 1,233.5경기초를 자동 진행 72,803.1ms에 완료했다(실효 약 16.94배). Main의 `growth.slice` 2,289회·16,914.3ms와 `frame.snapshot` 6,428회·18,216.7ms, 입력 준비 뒤 약 5초 지연이 관측됐다. Node 비교 경기가 겹친 기능 확인 표본이므로 통제된 성능 비교나 배속 합격으로 계산하지 않는다. 실제 생성 Worker의 별도 고립 실행에서 준비 신호 전 `window is not defined`를 확인했으며, 이 표본은 새 Worker의 성공 실행이 아니라 기존 Main 대체 경로다.

API 주소 초기화는 실제 호스트의 `globalThis.window`를 확인하며 Worker에 가짜 `window`나 계정·네트워크 접근을 추가하지 않는다. 새 엔진 `18b0405b…`, 빌드 `aN-OY3-uBIlp0eJc5jKGs`의 생성 Worker와 실제 공유 청크는 준비 신호 및 첫 페이즈 140초·701프레임·정상 완료를 고립 VM에서 통과했다. 검사에는 현재 소스·생성 지문·실제 경로 및 의존 청크 연결을 포함한다. 첫 검사에서 API 파일 전체의 정상 브라우저 분기를 금지하던 오판은 초기화 함수 범위로 바로잡았다.
