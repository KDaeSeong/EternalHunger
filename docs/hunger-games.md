# 헝거게임 시뮬레이터

플레이 주소는 `/hungergames`다. 게임 허브와 사이트 메뉴에서 이터널 헝거와 별도로 선택한다. 게스트는 샘플 8명과 기본 사건 43개로 바로 시작하거나 참가자를 편집할 수 있다. 장비 제작이나 ER 능력치 설정은 요구하지 않는다.

## 참가자와 특성

참가자 탭에서 이름, 사진, 팀/구역, 시작 아이템, 헝거게임 특성을 설정한다. 동일한 팀은 기본 전투·배신 사건에서 서로 싸우지 않는다. 팀은 전원 생존을 보장하지 않으며 환경 사건의 적용 여부는 각자의 특성으로 판정한다.

캐릭터 설정 화면의 기본 정보에도 `hungerTraits` 편집을 제공한다. `/characters/save` 저장, editor/stats/simulation 조회, 클라이언트와 서버의 저장 후 검증에서 이 필드를 유지한다. 옛 클라이언트가 필드를 보내지 않으면 기존 값은 보존한다. 헝거게임 화면에서 내 캐릭터를 불러오면 이름·사진·특성을 가져오며, 여기서 편집한 참가자 설정은 해당 헝거게임 작업 공간에 저장된다.

특성은 이름이나 스킬 설명에서 추측하지 않는다. 샘플 라이덴 쇼군의 면역·전투 숙련, 불꽃 정령의 불 조종·정령 신체·물리 면역, 기계 경비병의 물리 저항은 시뮬레이터에 명시적으로 지정한 설정이며 원작 설정을 자동으로 판정하는 기능은 아니다. `lightning_control`이나 `fire_control`만 지정하면 해당 공격·반격 사건에 참여할 수 있지만 면역은 얻지 않는다. `mechanical`이나 `elemental_body` 자체도 피해 면역을 주지 않는다.

기계와 정령은 기본 식사·열매·갈증·회상·생물 응급 처치 사건에서 제외하고 감지·절전·자가 정비 또는 기운 안정·형태 회복 사건에 참여한다. 손상·탈락 문구와 기록 배지도 신체에 맞게 표시한다. 두 신체 특성이 겹치면 기계 신체 표현을 우선한다. 일반 칼·근접 공격의 공격자는 별도 능력이 없는 참가자로 제한하고, 번개·불 조종자는 능력 공격이나 해당 능력 반격에 참여한다.

| 원인 | 면역 특성 | 저항 특성 |
| --- | --- | --- |
| 자연 번개 | `lightning_immune` | `lightning_resistant` |
| 화재 | `fire_immune` | `fire_resistant` |
| 익사 | `underwater_breathing` | 없음 |
| 독 | `poison_immune` | `poison_resistant` |
| 추위 | `cold_immune` | `cold_resistant` |
| 물리 공격 | `physical_immune` | `physical_resistant` |
| 번개 공격 | `lightning_attack_immune` | `lightning_attack_resistant` |
| 불 공격 | `fire_attack_immune` | `fire_attack_resistant` |
| 기타 전투·사고 | 없음 | 없음 |

면역은 해당 원인의 사망과 부상 효과가 포함된 결과 전체를 제외한다. 저항은 사망 결과의 상대 비중을 1/5로 줄인다. 면역·저항·일반 참가자에게 서로 다른 결과 문구를 등록할 수 있다. 정의한 특성 키는 32개 이내로 저장하며 추가 키는 고급 JSON에서 역할 조건으로 사용할 수 있다. 추가 키가 자동으로 피해 면역을 부여하지는 않는다.

자연 번개(`lightning`)와 번개 공격(`lightning_attack`), 화재(`fire`)와 불 공격(`fire_attack`)은 서로 다른 원인이다. 자연 피해 면역을 능력 공격 면역으로 확대 해석하지 않는다. 칼·주먹은 `physical`로 등록해야 물리 면역·저항이 적용된다. 옛 이벤트의 `combat`은 기타 전투 원인으로 유지한다.

공격자(`source`)가 지정된 피해 분기의 상대 비중에는 공격자의 전투 숙련 ×1.75, 피해자의 전투 숙련 ÷1.75, 공격자 부상 ×0.6, 피해자 부상 ×1.5를 반영한다. 비행 가능한 피해자는 물리 공격의 사망 비중을 추가로 절반으로 줄이고, 별도의 공중 회피 분기에도 참여한다. 결과끼리 비교하는 비중이므로 고정 승률이나 승리 보장은 아니다.

## 이벤트 등록

이벤트 탭에서 발생 시점(시작/낮/밤/연회), 일차, 날씨, 장소, 등장 빈도와 반복 제한을 지정한다. 역할은 1~4개이고 각 역할마다 필수/제외 특성, 건강·부상 상태, 필요 아이템을 설정한다. 두 역할 사이에는 같은 팀/같은 팀 제외/동맹/동맹 제외/적대 조건을 등록할 수 있다. 기본 공격 사건은 동맹을 제외하고, 동맹끼리의 공격은 배신 사건으로 처리한다.

최소·최대 생존자 수로 사건을 제한할 수 있다. `minDuelPhases`는 최종 두 참가자가 남은 뒤 경과한 페이즈 조건이며, 0이면 사용하지 않는다. 양수이면 최소·최대 생존자를 모두 2명으로 지정해야 한다. 최종 두 참가자가 만들어진 시점부터 계산하고, 시작 보급 페이즈와 같은 팀의 두 참가자는 최종 대치 압박에서 제외한다.

결과 분기는 1~12개다. 각각 조건, 빈도, 문구, 실제 효과를 갖는다. 지원 효과는 사망, 부상, 부상 회복, 아이템 획득·소모, 동맹, 적대다. 사망·부상에는 원인을 반드시 지정하고 선택적으로 공격자 역할을 지정한다. 사망 분기에만 처치 수를 올리며 부상 분기는 공격자만 기록한다. 한 참가자에게 사망·부상·회복을 동시에 등록하지 못하게 검증한다.

분기 참가자 조건(`requirements`)에서는 역할별 필수/제외 특성, 건강·부상, 필요 아이템을 추가로 지정한다. 모든 조건을 만족하는 분기만 선택한다. 예를 들어 `{ "role": "victim", "allTraits": ["mechanical"] }` 조건을 사용해 부품 손상 문구를 기계에게만 출력한다. 같은 역할의 조건을 중복 등록하거나 필수/제외 특성을 겹치게 등록할 수 없다. 면역 조건과 참가자 조건은 함께 적용한다.

문구의 `{actor}`, `{victim}` 같은 자리표시자는 해당 역할 참가자의 이름으로 바뀐다. 존재하지 않는 역할, 지원하지 않는 효과·원인, 잘못된 수치, 중복 역할, 필수와 제외가 겹치는 특성은 저장 시 거부한다. 문구를 분석해 참가자를 죽이거나 코드를 실행하지 않는다.

이름 자리표시자 바로 뒤의 은/는, 이/가, 을/를, 과/와, 으로/로, 이랑/랑, 아/야는 받침에 맞게 선택한다. ‘으로/로’는 ㄹ 받침이면 ‘로’를 쓴다. `{actor}은`, `{actor}은(는)`, `{actor}은/는` 모두 지원하고 반대 순서도 허용한다. 따옴표나 닫는 괄호로 이름을 감싼 경우도 처리한다. 복합 조사에는 `{actor}으로(로)부터`처럼 쌍을 표시할 수 있다.

| 문구 | 이름 | 출력 |
| --- | --- | --- |
| `{actor}은` | 야전 의사 | 야전 의사는 |
| `{actor}과` | 숲의 생존가 | 숲의 생존가와 |
| `{actor}을` | 라이덴 쇼군 | 라이덴 쇼군을 |
| `{actor}으로` | 노엘 | 노엘로 |

분리된 한글 자모는 NFC로 받침을 판정하고 원래 이름 표기는 보존한다. 뒤의 문장 부호·장식은 발음에서 제외하며 끝 숫자는 한국어 숫자 읽기를 따른다. 외국 문자만 있는 이름의 발음을 추측하지 않고 ‘은(는)’ 같은 쌍으로 표시하므로 정확한 한국어 발음이 필요하면 이름을 한글로 적는다. 이름 안의 문자, 일반 단어, 자리표시자와 무관한 문장은 바꾸지 않는다. 조사 처리는 경기·시험 판정·휴식·저장 복원에 공통으로 적용한다.

빈도는 현재 가능한 사건 또는 분기 사이의 상대 비중이다. 참가자 조건, 면역, 아이템, 마지막 생존자 보존으로 후보가 달라지므로 전체 경기에서의 고정 백분율을 뜻하지 않는다. 쉬어 갈 페이즈 수가 0이면 연속 등장할 수 있다. 1이면 등장한 페이즈와 그다음 페이즈를 건너뛴다. 최대 등장 횟수 0은 횟수 제한 없음이다.

시험 판정에서 참가자를 역할에 직접 배정하고 시점·날씨·장소, 역할별 부상 여부, 시험 생존자 수와 최종 2인 대치 경과 페이즈를 골라 현재 가능한 결과와 실제 상태 변경을 확인한다. 시험은 실제 경기와 별도의 시드를 사용하며 실제 참가자·경기 진행·난수 상태를 변경하지 않는다. 참가자가 2명 이상 있어야 시험할 수 있다.

### 낙뢰 예시

고급 JSON의 핵심 구조는 다음과 같다. 생략한 시점·날씨·장소는 모두 허용하는 기본값이다.

```json
{
  "id": "custom-lightning",
  "title": "갑작스러운 낙뢰",
  "roles": [{ "key": "actor", "label": "피해자" }],
  "outcomes": [
    {
      "label": "면역",
      "when": { "role": "actor", "cause": "lightning", "protection": "immune" },
      "text": "{actor}은 번개를 맞고도 태연하다.",
      "effects": []
    },
    {
      "label": "회피",
      "text": "{actor}은 낙뢰를 피한다.",
      "effects": []
    },
    {
      "label": "사망",
      "text": "{actor}은 낙뢰를 맞고 목숨을 잃는다.",
      "effects": [{ "type": "death", "target": "actor", "cause": "lightning" }]
    }
  ]
}
```

면역 참가자는 위 사망 분기에 별도의 면역 조건이 없어도 사망하지 않는다. 면역 분기와 회피 분기 중 가능한 결과만 뽑는다. 사망 문구를 넣고 효과 원인을 전투로 잘못 지정하는 등 문구와 효과의 의미를 일치시키는 작업은 제작자의 책임이다. 미리보기로 확인한다.

## 경기와 저장

시작 후 낮·밤을 번갈아 진행하고 4일차 낮은 연회다. 매 페이즈의 날씨·장소는 시드로 정한다. 참가자는 페이즈마다 최대 한 사건의 역할을 맡는다. 역할 전체와 결과가 성립하는 후보를 찾고, 무작위 선택 후 결과를 한 번에 반영한다. 죽은 참가자와 중복 배정은 실행 직전에도 확인한다. 아이템이 없거나 면역 때문에 결과가 성립하지 않으면 일부 효과만 적용하지 않는다. 후보가 없으면 안전한 휴식으로 진행한다. 조합 탐색도 사건당 최대 12,000단계로 제한한다.

같은 페이즈에서 직전에 나온 사건은 다른 유효한 사건이 있으면 연속 선택하지 않는다. 같은 페이즈의 반복과 최근 세 페이즈의 전체·동일 참가자 반복도 비중을 낮춘다. 대치 사건은 일반 휴식보다 반복 감점을 작게 하고, 후반·소수 생존 때 비중을 최대 네 배로 높여 경기가 휴식에만 머물지 않게 한다. 면역과 팀·동맹·아이템 조건을 무시하지 않으며, 유효한 사건이 하나뿐이면 반복을 허용한다.

최종 두 참가자의 대치가 길어지면 공격 사건 비중을 추가로 최대 12배 높이고, 휴식 비중을 낮춘다. 피해 분기는 결정타 비중을 최대 12배, 부상 비중을 최대 3배로 높이고 회피·퇴각 비중을 줄인다. 두 참가자만 남은 뒤 2페이즈가 지나면 근접·번개·불꽃 결전 사건도 등장한다. 동맹이던 두 참가자도 결전에서 명시적으로 적대 관계로 바뀌며, 같은 팀 제외와 피해 면역은 계속 유지한다. 양쪽 모두 가능한 공격에 면역이면 사망을 만들지 않고 진행 한도에서 공동 생존으로 끝낸다.

최후의 한 명이 남으면 즉시 종료한다. 모든 생존자를 동시에 죽이는 분기는 제외한다. 기본 진행 한도는 60페이즈이며 1~120으로 설정할 수 있다. 한도에 도달했을 때는 남은 인원을 공동 생존으로 표시하고 억지로 면역을 무시해 우승자를 만들지 않는다. 참가자 최대 64명, 이벤트 최대 200개, 시작 아이템 최대 12개를 지원한다.

같은 참가자·이벤트·시드·한도로 다시 시작하면 같은 경기다. 시작할 때 입력을 복사하므로 편집은 다음 경기에만 적용된다. 이전 기록을 읽는 동안 참가자 상태 패널은 현재 경기의 상태를 표시한다.

브라우저에 자동 저장하며 JSON 가져오기/내보내기를 지원한다. 로그인한 사용자는 기존 `/game-saves/hunger-games/workspace` 슬롯으로 저장·불러오기한다. 공용 저장 API의 기본 계정 용량 한도는 1MB이므로 사진이 많으면 JSON을 쓰거나 사진 용량을 줄인다. JSON은 최대 6MB다. 자동 저장 실패는 화면에 표시하고 마지막 정상 저장을 보존한다. 읽을 수 없는 기존 저장을 자동으로 덮어쓰지 않는다.

저장은 `hunger-games.v1` 형식, 입력 설정, 진행한 페이즈 수와 경기의 판정 규칙(`run.rulesVersion`)을 보관한다. 규칙 필드가 없는 기존 저장은 이전 규칙 1로 복원해 진행·승패·난수·처치 기록을 유지하고 문구·상태 표시를 보정한다. 새 경기는 규칙 2로 시작한다. 지원하지 않는 규칙 버전은 거부한다. 불러올 때 결정적 재실행으로 상태와 사건 기록을 복원한다. 문구·임의의 생존자 목록을 진실로 받아들이지 않는다. 편집한 다음 경기 설정과 진행 중인 경기 입력이 다르면 둘을 각각 보존한다. 초상 이미지는 사건 기록마다 복제하지 않는다.

기존 22개 기본 사건을 전혀 수정하지 않은 저장은 다음 경기용 사건을 43개 구성으로 업데이트한다. 참가자는 이름·사진·팀·아이템·특성까지 원본과 동일한 샘플만 업데이트한다. 진행 중인 경기의 입력은 바꾸지 않는다. 사건을 수정하거나 추가·삭제한 작업 공간은 자동 변경하지 않으며, 이벤트 탭의 ‘기본 사건 업데이트’로 선택해서 적용할 수 있다. 이 버튼은 기본 사건과 같은 ID의 내용을 교체하므로 해당 수정 내용과 저장 전 초안을 초기화한다고 먼저 알린다. 다른 ID의 추가 사건과 수정한 참가자는 유지하고, 합친 사건이 200개를 넘으면 변경을 거부한다.

브라우저 복원은 두 페이즈마다 제어를 양보해 큰 경기의 재실행 중에도 화면이 응답할 수 있게 한다. 가져오기·계정 불러오기는 복원된 결과를 재사용해 같은 경기를 두 번 계산하지 않는다. 탭을 옮겨도 저장 전 이벤트 초안은 유지하며, 저장 파일과 실제 경기에는 이벤트 저장을 누른 내용만 반영한다.
