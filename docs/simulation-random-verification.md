# 경기 난수 분리와 재현 기반 검증

기준일: 2026-09-05. G5.1의 선행 작업이다. 이 문서의 경기 입력 JSON은 검사 도구의 입력이며, 사용자가 로컬 기록에서 경기를 불러오는 제품 기능은 아직 구현되지 않았다.

## 발견한 원인

- 시드 훅이 브라우저 전체의 `Math.random`을 교체했다. 초기 편성과 화면 처리까지 같은 난수를 소비하므로 시드만 같다고 같은 경기라고 보장할 수 없었다.
- 로그 ID를 React 상태 갱신 함수 안에서 난수로 만들고 순번을 변경했다. 갱신 함수의 지연/재실행이 경기 난수 소비에 개입할 수 있었다.
- 생성 장비와 개발자 선택 상자의 ID가 실제 시각에 의존했다.
- 생성 전설/초월 장비의 최근 이름 기록이 모듈 전체에 공유됐다. 중복 이름을 피하는 재추첨 횟수가 이전 경기나 다른 실행의 영향을 받았다.

## 구현

- 경기마다 난수 인스턴스를 두고 첫 페이즈 시작 시 초기화한다. 실제 시작 편성은 그 이전에 확정되므로, 같은 시드만으로 무작위 초기 편성이 복원된다는 주장을 하지 않는다.
- 성장·제작·전투·이동·부활·월드 생성의 난수 및 공유 전투/장비/상태 효과 도구를 경기 전용 호출 경계에 연결했다. 경기 밖의 공유 도구는 기존의 일반 난수를 사용한다.
- 비동기 경기 진행은 동기 계산 구간과 대기 구간을 나눈다. 대기를 시작하기 전에 난수 문맥을 해제하고, 재개 시 해당 경기의 문맥을 복구한다. 중첩 호출 및 예외 처리도 같은 규칙을 따른다. 전역 `Math.random` 자체는 바꾸지 않는다.
- 기존 FNV-1a/Mulberry32 수열을 유지한다. 난수 상태·호출 수·생성 ID 순번·최근 생성 장비 이름을 독립적인 JSON 값으로 꺼내고 복원할 수 있다. 잘못되거나 지원하지 않는 상태는 거부한다.
- 생성 장비 ID는 실제 시각 대신 경기별 순번을 사용하되 기존 한 번의 난수 소비를 유지한다. 장비 이름 중복 회피도 경기별 기록을 사용한다.
- 로그 ID는 기록 생성 시 한 번만 할당하며 화면 갱신 함수는 순수하게 유지한다. 페이즈가 바뀌어도 마운트 내 로그 순번을 재사용하지 않는다.
- 시드 안내를 실제 보장 범위에 맞췄으며 시작 후 입력과 적용을 잠근다.

## 회귀 기준선

수정 전과 난수 분리 후 각각 `check:action-timeline`로 기존 LCG 검사 입력 1101을 실행했다. 이 검사는 기존 입력/수열의 유지 여부를 확인하는 용도로, 새 제품용 시드의 브라우저 재현 시험과는 다르다.

- 13페이즈, 20:52, 2팀 승리
- 1,278개 프레임, 15회 부활, 관전 읽기 34회, API 요청 0
- 전체 사건 해시가 동일했다.

`bac03f684c718171e0ca05c1de584dc22d9d32c8fe90b87a62cbc72c54cf7063`

## 새 난수 격리 검사

`client/scripts/check-simulation-random.mjs`와 `scripts/lib/run-random-isolation-match.mjs`는 다음을 검사한다.

1. 여러 문자열 시드에 대해 이전 구현과 각각 1,000개 난수 일치
2. JSON 복원 이후 난수와 중복 없는 장비 ID의 연속성
3. 지원하지 않는 알고리즘, 잘못된 정수/이름 기록 및 중복 기록 키 거부
4. 중첩 동기 실행 및 예외 뒤 문맥 복구, 전역 난수 함수 불변
5. 비동기 실행 두 개 및 화면 난수 사이의 독립성
6. 대기 실패 후 catch/finally 및 전파되는 예외의 문맥 복구
7. 실제 전투/상태 효과/무기 선택/생성 장비 도구의 난수 및 시각 격리
8. 지연하거나 반복 실행한 로그 갱신 함수의 순수성
9. 전설 장비 이름 기록의 경기별 분리, JSON 복원, 동시 생성 일치
10. 경기 라이브러리의 직접 난수 호출 방지와 페이지 연결 확인
11. 실제 전체 경기의 사건·상태·로그·난수 상태 일치

전체 경기 비교는 동일한 시작 편성 24명, 지도, 실제 774개 아이템 카탈로그, 설정, 경기 시드 `1101`을 JSON으로 복제해 사용한다. 기준 경기 하나를 완료한 뒤, 같은 입력의 두 경기를 동시에 실행한다. 비교 경기에서는 다음 조건을 바꾼다.

- 화면용 일반 난수 추가 소비 및 추가 비동기 대기
- 로그 갱신의 지연 및 반복 호출
- 실행 중 배속 1/8/32 변경
- 관전 팀 변경과 현재 상태 읽기
- 진행 중 상태 반영 또는 페이즈 종료 때만 상태 반영
- 페이즈 사이 난수 상태를 JSON으로 복원

API 요청은 금지하며, 화면용으로 명시한 코드 이외에서 일반 난수를 호출하면 실패한다. 우승자만 비교하지 않고 모든 사건, 매 프레임, 마지막 상태, 실제 로그, 최종 난수 상태를 비교한다. 실제 시각을 포함한 사건 진단용 `ts`만 의미 비교에서 제외한다.

생성 이름 기록 분리까지 포함한 난수 검사 11/11 통과. 기본 경기 3회는 모두 다음과 일치했다.

- 13페이즈, 20:57, 3팀 승리, 1,283개 프레임
- 전체 사건 5,494개, 경기 난수 9,630회, 비교 두 경기의 화면 난수 추가 소비 총 53,158회, API 요청 0
- 사건 해시: `264f374aca959ecaa21419b1d781d938b6406cf24ba520eb1c28866ad8c48c2e`
- 프레임 해시: `bd67ac7e1664f44d3e0b994e83fdc3b332f9a599f28e3e2ac2e5ab6068bf2f37`

이 기본 경기에서는 실제 카탈로그 장비를 사용하므로 임의 생성 장비 ID는 0개다. 생성 장비/전설 이름의 격리는 별도의 실제 생성 도구 검사에서 확인했으며, 기본 경기 해시만으로 그 경로까지 검증했다고 주장하지 않는다.

## 기존 검사 도구 수정

- 새 공용 난수 모듈은 Node의 직접 모듈 검사에서도 불러올 수 있도록 명시적 `.js` 경로를 사용한다.
- 부활 검사는 import를 삭제하고 일부 의존성을 흉내 내던 실행 방식을 제거했다. 실제 부활·팀·키오스크·상태 정규화·세계 시계 모듈을 사용하며, 낮 페이즈 입력을 제품의 실제 값인 `morning`으로 맞췄다. 기존 여섯 부활 경계/비용 검사 모두 통과했다. 게임 부활 규칙을 검사에 맞춰 변경한 것은 아니다.

## 최종 통합 및 브라우저 검사

- 최종 소스의 `cmd /c npm run check:eternal-hunger`: 종료 코드 0. 난수 11/11, 기존 시간축 10/10, 부활 6개, 성장/자원/팀/관전/종료/게스트 저장 등의 회귀 검사, 런타임 검사, 프로덕션 빌드가 모두 통과했다.
- 해당 빌드를 `127.0.0.1:3102`에서 실행했다. 비로그인으로 24명/8팀을 구성한 별도 브라우저 경기다. 검사 도구의 저장 입력과 같은 경기라고 주장하지 않는다.
- 시드의 실제 보장 범위를 설명하는 새 문구와 현재 시드 `1788542576577`을 확인했다. 개발자 확인창에 승인 동작을 보내지 않았으며, 열려 있던 도구 패널을 닫고 진행했다. 아이템 지급·장비 변경·강제 소모품 사용은 하지 않았다.
- x8 자동 진행으로 2팀을 관전했다. 진행 중 전체 로그를 열어 제작/이동 로그를 확인하고 전투 상세 보기로 전환했다. 팀 관전으로 돌아와 6팀을 선택하고 x32로 바꿨다.
- 03:47에 6팀 구름/라온/백로의 현재 HP, 위치, 성장 1/5가 보였다. 06:23 스크린샷에서 구름의 성장 2/5, 금지구역 2개, 생존 21/사망 3이 표시됐다.
- 12:32의 독립 로그창은 앞서 고른 전투 상세 모드를 유지했다. 그 페이즈의 해당 시점에는 전투 상세가 아직 0개였으며, 이를 로그 표시 오류로 판단하지 않았다. 뒤의 6팀 관전은 전원 사망과 처치자 여울/별하/미르를 유지했다.
- 로그창을 닫고 7팀으로 전환했다. 17:43에 미르/별하/보라가 병원에 모여 있었고 세 명 모두 목표 장비 5/5였다. 팀 공통 목표와 당시 처치/지원 수가 표시됐다.
- 21:03에 미르가 가람을 처치하고 보라/별하가 지원한 마지막 기록으로 종료했다. 7팀 생존 3/3, 전체 생존 3/사망 21, 팀 10처치/6어시스트가 멤버별 합계(미르 4/1, 별하 2/2, 보라 4/3)와 일치했다.
- 결과 창에서 같은 종료 시각, 마지막 탈락 원인 `교전`, 로컬 완주 기록 `완료`를 확인했다. 소모품 요약은 auto 32/dev 0이었다. 브라우저 경고/오류 목록은 비어 있었다.
- 시드 입력의 시작 후 잠금은 소스/빌드 검사 범위다. 이번 브라우저 완주에서는 개발자 패널의 잠금 동작을 별도로 조작하지 않았다.
- 검증용 탭을 닫았다. `Get-NetTCPConnection`/`Get-CimInstance` 조회는 접근이 거부되어 PID를 추정하지 않았다. 대신 이번에 서버를 실행한 터미널 세션에 종료 신호를 보내 종료 코드 1을 확인했다. 이후 `netstat`에서도 3102 포트 연결이 남지 않은 것을 확인했다. 배포·계정 변경은 하지 않았다.

## 아직 완료가 아닌 범위

- 저장한 경기 입력을 제품의 로컬 기록에서 불러와 재경기하는 기능
- 시작 편성의 전체 능력치/장비/경로, 지도, 규칙, 카탈로그 및 실행 버전 보존과 호환성 확인
- 전체 사건 저장/비교 경로. 현재 화면의 최근 5,000개 사건 보관은 전체 리플레이가 아니다.
- 구버전 지도의 지역별 상자 제한은 `fieldLootRuntime`에서 로컬 설정을 읽는 경로가 남아 있다. 저장 입력 구현 시 실제 적용값을 시작 입력으로 확정해야 한다.
- 새 편성/전략의 비교 UI와 폭넓은 균형 평가, 실제 사용자의 이해·재플레이 평가

기본 입력의 일치와 브라우저 완주는 모든 사용자 지도/규칙의 재현성, 재미, 계정 서비스의 가치를 증명하지 않는다.
